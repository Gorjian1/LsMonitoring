# Brief: LoadSensing LS-G6 Monitoring Tool

## Контекст задачи

Нужно написать desktop-тулзу для мониторинга в реальном времени данных с
наклонометра **LoadSensing LS-G6-INC15** (биаксиальный MEMS-инклинометр ±15°,
производитель Worldsensing). Датчик подключён к гейтвею **CMT Edge** через LoRa.
Гейтвей доступен по Ethernet (link-local IP `169.254.0.1`).

Цели:
- Реалтайм-визуализация данных (графики A-axis, B-axis, температуры)
- Алармы при превышении настраиваемых порогов
- Экспорт исторических данных в Excel
- Поставка одним `.exe` под Windows (через PyInstaller)

Заказчик (начальник) не разработчик. Установка и запуск должны быть
максимально простыми — двойной клик по экзешнику.

## Источник данных — стратегия

Гейтвей поддерживает 3 интерфейса в текущей прошивке: **FTP push, ModBus TCP,
Compacted CSV**. MQTT и REST API в этой прошивке нет.

**На MVP делаем HTTP-скрейпинг CSV** — самый быстрый путь:
- В админке гейтвея каждой ноде доступен URL вида
  `http://169.254.0.1/dataserver/node/view/<NODE_ID>` со ссылкой на
  `<NODE_ID>-readings-current.csv`.
- Авторизация — **HTTP Basic Auth** (нативный диалог браузера, не HTML-форма).
  Дефолтный пользователь `admin`, пароль выдаётся в Gateway Information Sheet.
- Полученные значения уже в инженерных единицах (градусы, °C) — парсить и
  показывать.

**Параллельно закладываем абстракцию для Modbus TCP** (порт 502, Unit ID 1-255
маппится на Node ID в админке). Точная register map у поставщика, мы её ещё не
получили. Сделай интерфейс `DataSource` так, чтобы Modbus-реализацию можно было
добавить потом, не переписывая GUI и логику алармов.

**FTP не используем** — лишний геморрой с поднятием FTP-сервера на стороне
тулзы.

## Структура CSV (по образцу `fixtures/sample_readings.csv`)

Первые ~9 строк — метаданные:
```
"Node ID",6989
"Gateway ID",13456
"Model","LS-G6-INC15"
"Hw version",
"Fw version",
"Location Lat",
"Location Lon",
"Created time","2026-05-05 09:58:58"
"Timezone","Europe/Amsterdam"
```

Затем строка-заголовок данных:
```
"Date-and-time","Temp-6989-Ch1","Aaxis-6989-Ch1","Baxis-6989-Ch1","AaxisVariation-6989-Ch1","BaxisVariation-6989-Ch1"
```

И строки данных. **Важно**: количество колонок в строках данных может быть
МЕНЬШЕ чем в заголовке. В тестовом файле колонки `AaxisVariation` и
`BaxisVariation` пустые (не заполняются пока на ноде не задана reference point —
"нулевая позиция"). Парсер должен это переживать.

Имена колонок A/B/Variation **зависят от Node ID и канала** (`Ch1`, может быть
`Ch2` и т.д. на других моделях нод). Парсить надо по паттерну, не по фикс-именам.

## Sentinel-значения (КРИТИЧНО)

В тестовом файле периодически встречаются значения вокруг **±18.74** и **±18.59**
по осям A/B. Диапазон сенсора по даташиту **±15°**, поэтому такие значения —
overflow / error code от датчика, **не реальный наклон**.

Юзер подтверждает что глитчи в его данных могут быть от физического вращения
датчика во время теста (он его крутил), но в любом случае значение вне ±15°
обрабатывается как невалидное.

**Правило**: `abs(value) > 15.0` → значение не отображать как наклон, а
маркировать как `INVALID`. См. ниже про пользовательскую настройку поведения
при невалидных данных.

## Технические требования к тулзе

### Источники данных

- Класс `DataSource` (abstract): методы `connect()`, `fetch_latest()`,
  `fetch_history(since)`, `discover_nodes()`, `disconnect()`.
- Реализация `CsvScraperSource` — работает сейчас.
  - Параметры: gateway IP, login, password, polling interval.
  - `discover_nodes()` парсит `/networks/` или аналогичную страницу админки и
    возвращает список node_id с моделями. Если автоопределение не получится —
    fallback: пользователь вручную добавляет node_id.
  - `fetch_latest()` качает CSV ноды, возвращает последнюю валидную строку
    (или маркер INVALID).
- Реализация `ModbusSource` — заглушка-скелет с TODO. Класс должен
  существовать с правильной сигнатурой; внутри `NotImplementedError` или
  pyмodbus-каркас, который потом дополним по register map. **Не пытаться
  угадывать регистры** — без официального address map это обречено.

### GUI

Стек: **PySide6 + pyqtgraph** (графики), `pandas` для парсинга,
`openpyxl` для экспорта. matplotlib НЕ использовать — медленно для real-time.

Главное окно:
- Сверху: панель статуса подключения (зелёный / красный кружок, IP, время
  последнего ответа от гейтвея).
- Список нод слева (auto-discovered или добавленные вручную). Клик по ноде —
  её данные справа.
- Справа на ноду: график temperature + A-axis + B-axis на одной временной
  оси. Использовать pyqtgraph с автоскроллом и буфером последних N точек
  (настраиваемо, по умолчанию 1000).
- Невалидные значения (sentinel'ы или потеря связи) показывать **серой
  заливкой полосы** на графике в этом интервале времени — НЕ просто
  пропускать (юзер должен видеть что данные были невалидны, а не "график
  чистый, всё ок").
- Подсветка фона графика красным когда любой из текущих параметров превышает
  alarm threshold.
- Под графиком — таблица последних N измерений с цветовой маркировкой
  состояния (норма / warning / critical / invalid).

### Настройки (диалог, сохраняются в `config.json` рядом с .exe)

1. **Подключение**: gateway IP, username, password (НЕ хардкодить — попросить
   юзера ввести при первом запуске; пароль шифровать или хотя бы кодировать
   base64 в config'е, не plaintext).
2. **Polling interval** — как часто опрашивать CSV (по умолчанию 10 сек,
   диапазон 5 сек — 5 мин). Это период HTTP-опроса, не sampling rate ноды!
3. **Sampling rate ноды** — если в CSV / на странице ноды видно текущий
   sampling rate, отображать его. Менять sampling rate ноды через тулзу
   **не пытаться** — это делается через Android-приложение Worldsensing
   физическим подключением к ноде USB-кабелем, web-интерфейсом не меняется.
4. **Тип порога** — выбор пользователя:
   - `absolute` — порог по абсолютному углу (`|A| > X°` или `|B| > X°`)
   - `variation` — порог по variation от reference (если колонки Variation
     заполнены; если пустые — disable этого варианта в UI с подсказкой
     "задайте reference point в админке гейтвея")
5. **Пороги**: warning + critical, отдельно для A и B (или общий — checkbox
   "одинаковые для A и B").
6. **Поведение при невалидных значениях** — radio:
   - `hide` — игнорировать тихо (рисовать серым)
   - `mark` — показывать как ошибку датчика, но без аларма
   - `alarm` — считать невалидное значение критическим алармом если длится
     дольше N минут (настраиваемо, по умолчанию 5 мин)
7. **Алармы** — что делать при срабатывании:
   - звуковой сигнал (системный beep — кросс-платформенно)
   - всплывающее окно на передний план
   - запись в alarm log (отдельный CSV рядом с экзешником)
   - (опционально, если успеешь) email — но это nice-to-have, не на MVP

### Экспорт

- Кнопка "Export to Excel" — выгружает все накопленные данные текущей ноды
  (или всех нод, выбор) в `.xlsx` через openpyxl: один лист на ноду, колонки
  как в исходном CSV + колонка `Status` (OK / INVALID / WARNING / CRITICAL).
- Кнопка "Open data folder" — открывает папку где тулза хранит локальный
  кэш данных.
- Локальный кэш: тулза должна **накапливать историю локально** (SQLite или
  parquet), потому что гейтвей в `current.csv` отдаёт ограниченное окно. При
  старте подгружать локальную историю в график.

### Архитектура / качество кода

- Один общий event loop через Qt (`QTimer` для polling).
- Long-running операции (HTTP-запросы) — в `QThread` или `asyncio` через
  `qasync`, чтобы UI не подвисал.
- Логирование через `logging` в файл рядом с экзешником + ротация по дням.
- Все строки UI готовы к локализации (русский — основной, английский — резерв).
  Минимум — вынести в один словарь, не разбрасывать по коду.

## Что НЕ делать

- Не хардкодить креды в коде. Пароль гейтвея в данном случае случайно
  засветился в скрине — юзер его поменяет, в коде должна быть
  параметризация.
- Не угадывать Modbus-регистры — без официальной address map от
  Worldsensing это бесполезно.
- Не пытаться менять конфиг ноды (sampling rate и т.п.) через тулзу —
  Worldsensing для этого делает только Android-приложение через USB.
- Не трактовать отсутствие новых данных как фатальный disconnect — нода
  батарейная, спит между измерениями, gaps в данных нормальны. См. ниже.

## Замечание про природу данных (важно для UX)

Нода LS-G6-INC15 — батарейная LoRa. Она спит между измерениями и просыпается
ровно для одного замера + отправки пакета. Гейтвей кэширует последний
полученный пакет.

Это значит:
- "Real-time" в этой системе ограничен sampling rate ноды (минимум 30 сек,
  обычно 5-60 минут чтобы батарейка жила годами).
- Параметр **Message timeout** в админке Modbus — сколько гейтвей считает
  закешированные данные актуальными. По умолчанию 12 часов.
- Иногда LoRa-пакет теряется (помехи) — нода НЕ делает retry, ждёт
  следующего цикла. Это нормально, не disconnect.

UI должен:
- Показывать timestamp **последнего реального замера** (из CSV), не время
  опроса.
- Только если последний замер старше `sampling_rate × 3` (или фикс. таймаут
  типа 30 мин) — отрисовать индикатор "связь с нодой потеряна".
- На графике пробелы во времени отрисовывать корректно (не интерполировать
  прямой линией через дыру).
